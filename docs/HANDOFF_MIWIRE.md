## 3. APK Signing, Backups & In-Place Upgrade Guarantees

1. **Can future APKs be installed directly over the current APK without uninstalling?**
   - **YES** for all **`com.miwire`** builds (`versionCode >= 321`):
     - CI signs release builds (`miwire-release` / `MiWire.apk`) using persistent repository secrets (`MIWIRE_KEYSTORE_BASE64`, alias `CN=MiWire Release`, cert SHA-256 `eaacc7635946a1824d69bc6d1ee743d78adadfe2d70734aee3194a75040a2f6d`).
     - CI signs debug builds (`com.miwire.debug`) using persistent secret `MIWIRE_DEBUG_KEYSTORE_BASE64`.
     - As long as `applicationId` remains `"com.miwire"` (never renamed) and `versionCode` monotonically increments (`321 -> 322 -> ...`), Android PackageInstaller and `adb install -r` upgrade directly over the installed APK while preserving PC pairings, certificates, and settings.
2. **Relationship with the Stable Backup (`com.miware`):**
   - Tag `backup-v0.3.0-estavel` (commit `494d377a`) and GitHub Release `v0.3.0-miware` preserve the pre-refactor **`com.miware`** (`versionCode = 320`, `14,622,630` bytes, SHA-256 `572CEBCEB5D47D410091CDBF2088762E2AE523C93A3D7DE0D5D42F7F1CF975FF`, signed with `CN=Starwire MiBox`).
   - Because `com.miware` and `com.miwire` have **different** package IDs and signing certificates, `com.miwire` installs **side-by-side** with `com.miware` and will never overwrite it.
3. **Android Keyboard Accessibility Service Constraint:**
   - Android forbids APKs from auto-enabling their own `AccessibilityService` (`KeyboardAccessibilityService`) at install time without ADB (`WRITE_SECURE_SETTINGS`), root, or Device Owner privileges (e.g., *Install With Options*). Settings displays live status and a one-click Accessibility shortcut.

## 5. Critical Invariants & Engineering Decisions (Do Not Regress)

1. **Ghost Overlay (`Game.java` & `MediaCodecDecoderRenderer.java`):**
   - Amlogic Hardware Composer drops into overlay bypass and throttles CPU clocks if no View layer invalidates at least periodically, causing 8-10+ pacing skips when stats are off.
   - **Rule:** Keep the invisible `0x01000000` (alpha 1/255) `1 Hz` Ghost Overlay text swap on the UI thread when stats are disabled; **never** re-attach `perfListener` work (`VulkanRenderer::mutex_` lock + stats formatting) onto the video decode/render thread when telemetry is hidden.
2. **Sustained Performance (`PreferenceConfiguration.java` & `Game.java`):**
   - On Android TV / S905X5M, `setSustainedPerformanceMode(true)` caps CPU/GPU clocks low and harms 60 Hz pacing spikes. Default is `false` (`v9`), relying on ADPF (`AdpfHelper` + Vulkan `PerfHint`). Keep it opt-in.
3. **WAN `MiBox60Hz` Frame Pacer (`app/src/main/jni/vulkan/frame_pacer.cpp`):**
   - The integration uses a 10 ms transit-buffer cap and a decay divisor of 32. The v320 backup used 7 ms and a faster decay. Section 12 compares both presets on the same inputs.
4. **Menu / UI Shell Optimizations (Strictly Outside Streaming):**
   - `StarfieldView`: `85 ms` (`~12 FPS`) twinkle update gate + precomputed `STATIC_STAR_ALPHA` (pixel-identical frame 0 for Roborazzi).
   - `Rainbow`: `66 ms` (`~15 FPS`) animation update gate for wordmark shader shift and `Rainbow.Ring` sweep rotation.
   - `GenericGridAdapter`: static `ViewHolder` (`imgView`, `overlayView`, `txtView`, `prgView`, `settingsIndicator`, `boundTag`) avoids 5 `findViewById` lookups per tile bind.
   - `AppGridAdapter`: cached `density`, `SparseBooleanArray` custom-settings cache via `AppPreferences.hasCustomSettings`, single reused `Rainbow.Ring`, direct visible-tile D-pad selection mutation in `setSelectedAppId` (skipping full `notifyDataSetChanged()` grid rebinds), plus `shutdown()`.
   - `CachedAppAssetLoader`: `30 s` idle-timeout executors with `allowCoreThreadTimeOut(true)`, explicit `shutdown()` called from `AppView.onDestroy()` (eliminating thread leaks on activity exit), and a single GPU `ViewPropertyAnimator` `alpha(1f)` fade (`140 ms`).
   - `DiskAssetLoader`: API 28+ `ImageDecoder.setTargetSize` divided by `Math.max(1, sampleSize)`.
   - `PcView` / `AppView`: visible-field diff guard before `pcGridAdapter.notifyDataSetChanged()`, `onWindowFocusChanged` pausing `AppView` endless loops, and `CoverGlow.rememberedTintOrDefault` applying saved hero accent colors immediately before async box-art decode completes.

## 6. Known Hardware Limits Reached & Remaining Backlog

### Hard Technical Limits (Platform / Hardware Bound)
- **75 Hz monitor on the maintainer's Mi Box:** The reported HDMI mode is **1080p60**, with about 16.67 ms between refreshes. The active mode and other modes exposed by this HDMI chain can be read on the device.
- **USB 2.0 Single OTG Bus:** Ethernet, keyboard, mouse and the gamepad dongle share one USB controller. The client's 1 ms batching window handles motion already delivered by Android. Hardware polling jitter and contention require measurement on the Box.
- **2 GB Shared RAM:** In MiBox mode the application requests four swapchain images when presenting ahead, subject to surface capabilities. Its import cache holds up to 16 entries. These software targets changed between v320 and v322 (see section 9).
- **Cloud WAN RTT (Azure Tesla T4):** Internet packet jitter sets the physical floor for buffer headroom (`<= 10 ms` buffered in `MiBox60Hz`).
- **Auto-Enabling Accessibility:** Blocked by Android security model without ADB/DeviceOwner/root.

### Non-Blocking Repo Cleanups (Optional Future Work)
- Legacy credit strings in `app/src/main/res/values/strings.xml` (`title_about_github`, `credit_*`) and URLs in `OpenSourceNotices.java` still reference Starwire / upstream links (note: `RepoConsistencyTest` asserts README Credits URLs match `AboutCredits.ALL` / `OpenSourceNotices.ALL`!).
- `github/workflows/gemini.yml` sits in `github/` (missing leading dot) rather than `.github/workflows/`.
- The sync workflow targets `main`. It selects the upstream README or changelog on a conflict in those files, pushes first and requests a build afterwards. The debug artifacts are `miwire-debug` and `miwire-debug-tests`.
- Windows companion tools (`windows/StarwireMicReceiver.cs`, `windows/StarwireUsbHelper.cs`) preserve wire labels `"starwire-mic/1"` / `"starwire-usb/1"` — update both ends together if ever renamed.
- `release/MiWire.apk` tracked in Git increases repo clone size over time; releases can alternatively rely on GitHub Release assets only.

### Rede, periféricos, energia e temperatura

- **Rede e USB.** O produto oferece Wi-Fi 6 de 2,4/5 GHz, Bluetooth 5.2 e uma porta USB 2.0. No setup com fio, o adaptador Ethernet e todos os dispositivos de entrada usam o mesmo hub. A 35 Mb/s, o vídeo equivale a aproximadamente 4,38 MB/s antes de áudio, correção de perdas e cabeçalhos. Para saber onde um pico começou, importam a taxa negociada no adaptador, quadros perdidos pela rede, variação do RTT na WAN, tempo de decodificação e intervalo de apresentação. A quantidade de periféricos por si só não identifica o gargalo. [Ficha Xiaomi](https://www.mi.com/uk/product/xiaomi-tv-box-s-3rd-gen/specs/) · [Leitura das métricas Moonlight](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions)
- **Resposta dos comandos.** A janela de 1 ms no núcleo C controla como o cliente agrupa eventos de movimento antes de enviá-los. O polling do mouse, o dongle, a entrega de eventos pelo Android, a ida ao host, o processamento do jogo e o retorno da imagem têm tempos próprios. O intervalo completo entre apertar um botão e enxergar o resultado requer medição de ponta a ponta. [Núcleo C usado pelo projeto](https://github.com/Gustavo14832/MiWire/tree/b97c6e3a/src)
- **Energia e calor.** 2,5 GHz é o pico anunciado da CPU. O ADPF comunica ao sistema o trabalho previsto e realizado. O clock efetivo depende do firmware, da carga e do estado térmico. A faixa ambiente publicada para operação é de 0 a 40 °C. Uma atribuição de engasgos a aquecimento ou ao compositor precisa de observação na unidade durante o problema. [FAQ Xiaomi](https://www.mi.com/uk/support/faq/details/KA-567165/) · [ADPF](https://developer.android.com/games/optimize/adpf) · [Estado térmico no Android](https://developer.android.com/games/optimize/adpf/thermal)

### O que realmente mudou entre o ponto de restauração e a v322

Comparação do código da tag de backup com `f0dda75c`. Esses parâmetros mudaram juntos. O relato de que a v320 foi melhor serve como referência de uso e ainda não atribui o resultado a um parâmetro isolado.

| Comportamento | Código no ponto de restauração v320 | Código da v322 |
|---|---|---|
| Fila de jitter de vídeo no modo MiBox | Teto de 7 ms. Ao reduzir a fila, retira 1/4 da diferença quando ela passa de 2 ms e 1/8 no outro caso. | Teto de 10 ms e redução segundo o divisor da linha do tempo, 32 no perfil inicial MiBox. Ambas usam janela nominal de 2,5 s e cobertura de 99%. |

Uma fila que encolhe mais rápido pode reduzir temporariamente a espera depois de uma rajada. Uma fila com maior margem pode absorver mais variação de chegada pela WAN. ### Evidência que falta da unidade do mantenedor

Em uma futura sessão com acesso à Box, as leituras mais discriminantes são o build do Android, o registro da ABI escolhida pelo Android para cada pacote, o decoder e o renderizador ativos e o modo HDMI medido durante o jogo. Para comparar a sensação das versões, guardar a cena e os parâmetros do host, a duração, o estado do overlay, a rota de rede e o estado térmico. Comparar perda de rede, tempo de decode e distribuição dos intervalos apresentados na mesma cena. Uma gravação externa de comando e tela mede a resposta de ponta a ponta quando essa for a pergunta.

Para identificar modelo, firmware e ABIs em uma conexão ADB já autorizada, bastam leituras de `ro.product.model`, `ro.build.display.id`, `ro.build.version.sdk` e `ro.product.cpu.abilist` via `adb shell getprop`. O campo `primaryCpuAbi` em `adb shell dumpsys package com.miware` e `adb shell dumpsys package com.miwire` registra a escolha por pacote instalado. `adb shell dumpsys display` mostra modos de tela reportados pelo sistema. Esta pesquisa foi documental, com inspeção local do backup e do código, sem uma sessão de streaming instrumentada.

## 12. Frame pacing da Mi Box a 60 Hz

**25 de novembro de 2026.** Alteração local `b57227f0fe37faeacf71ce7522fdf24b139db46b`. Comparamos a v320 (`494d377a`), a integração anterior de mouse e vídeo (`bbfb542f`) e a nova integração. O mantenedor relata até dois *skips* por minuto na v320, acompanhados de um pequeno engasgo visível. O ensaio desta etapa reproduz uma causa possível. A conexão Azure, o driver Mali e a unidade do mantenedor ainda não forneceram um registro de uma dessas ocorrências.

### O perfil real e as diferenças entre as versões

O perfil mede o período do monitor pelas notificações do Choreographer e fixa a proporção em um ciclo por quadro. O ramo de baixo atraso usa o timestamp do host com a estimativa de trânsito. Nesse perfil, `updatePhase()` deixa o ajuste de fase em zero e retorna antes da regressão que os outros modos usam para travar a fase. O rótulo histórico *phase-locked* era impreciso para esse caminho. A janela de trânsito é de 2,5 s com cobertura nominal de 99%, limitada pelo número de amostras. A v320 limitava o amortecimento a 7 ms e o reduzia por divisores 4 ou 8. A base mais recente permite 10 ms e reduz por 32. A quantidade pedida de imagens Vulkan para apresentação antecipada também passou de 6 a 4, sujeita aos limites da superfície. Na matriz abaixo, as duas bases deram os mesmos totais de intervalos vazios. O ensaio comparou as decisões do pacer e não exercitou pressão de memória ou aquisição de imagens no driver. [Diferenças históricas do fork](https://github.com/Gustavo14832/MiWire/compare/494d377a...f0dda75c)

Com `VK_GOOGLE_display_timing`, a imagem pronta pode entrar pelo caminho antecipado no thread de entrega dos quadros. O perfil chama `preferSingleVsync(2'000'000)` e começa com um ciclo de atraso de apresentação e 2 ms de margem. Os retornos do compositor podem alterar os dois parâmetros. Os testes antigos com 1,5 ms continuam úteis para esse outro valor. Sem a extensão, o renderer Vulkan escolhe um quadro no callback do VSync. Se o Vulkan inteiro falhar e a sessão cair na saída direta do MediaCodec, este pacer nativo sai do caminho. [Frame pacing com Vulkan no Android](https://developer.android.com/games/sdk/frame-pacing/vulkan) · [Timestamps de apresentação do Khronos](https://docs.vulkan.org/refpages/latest/refpages/source/VkPastPresentationTimingGOOGLE.html)

### O que mudou

1. **Uma notificação perdida podia prender quadros prontos.** Antes, se o próximo horário já estivesse reservado, o limite de antecipação só avançava com outro callback. Se um callback faltasse, a reserva antiga continuava ocupando a janela do aplicativo. Mesmo com vídeo pronto, um horário podia ficar vazio e o atraso acumulado podia acabar em descarte por fila cheia. Agora a decisão consulta o relógio monotônico sob o lock de renderização. Entre um e dois períodos desde a última notificação, um quadro pronto pode reservar o horário seguinte ao que já passou. Há limite de um único ciclo inferido. Na volta do callback, o primeiro quadro devido pode usar o horário livre se ainda houver margem antes do alvo de tela. Um horário já ocupado é protegido contra envio duplicado.
2. **Duas chegadas próximas no Vulkan sem a extensão.** Quando dois quadros consecutivos do host chegam agrupados, o fallback pode apresentar o mais antigo e conservar um candidato para o ciclo seguinte. A regra verifica a distância entre timestamps do host, a compressão do intervalo de chegada e a idade do quadro mais antigo, limitada a menos de dois ciclos. A reserva termina quando a fila esvazia ou um callback falta. Em um dos ensaios com rajadas, essa escolha elevou de 18,306 para 27,293 ms o maior p99 entre as seis fases para a espera do decoder ao horário escolhido. O custo acompanha a redução de engasgos naquele fallback.
3. **Medição de chegada, descarte e tela.** O 1% low anterior vinha de até 1.000 intervalos de chegada ao cliente. O painel agora identifica essa origem. No painel detalhado do perfil MiBox com a extensão, os percentis e o 1% low de tela usam até 600 intervalos reportados pelo driver, com pelo menos 100 amostras. O 1% low usa a média dos intervalos do 1% mais lento. O texto *screen gaps/60s* conta intervalos maiores que 1,5 períodos entre apresentações reportadas e mostra a duração do maior. Inclui pausas de conteúdo ou de entrega. Timestamps duplicados ou fora de ordem não contam duas vezes. Os totais de quadros descartados pelo pacer e por fila cheia aparecem separadamente desde a criação do renderer. Sem o retorno de apresentação, os percentis existentes recebem o rótulo *submit*. As estatísticas da nova janela são ordenadas apenas ao abrir/atualizar o painel e depois de soltar o lock. O registro de VSync também guarda o instante da decisão depois de obter os locks, além da hora de chegada do callback. O leitor aceita registros antigos.

### Matriz reproduzível

Usamos o C++ do pacer de cada revisão. Dez cenários × seis fases iniciais da tela (0, 3, 6, 9, 12 e 15 ms) × três revisões produziram 180 execuções. Cada uma gerou 36.000 timestamps de origem, aproximadamente dez minutos de vídeo. O modelo ordena chegadas e callbacks por tempo, aplica o limite real da fila e mede os horários escolhidos. A referência usa trânsito de 18 ms, variação determinística de até 3 ms quando indicada, seed fixa e callback 0,3 ms após o VSync. O ramo antecipado usa a margem inicial real de 2 ms. Os eventos raros começam após o aquecimento, no quadro/ciclo 300, e voltam a cada 1.800. A apuração exclui os primeiros 180 ciclos e a ponta final. GPU, aquisição da swapchain, aprendizado de margem sob carga e monitor físico ficam fora desse modelo.

**Células da tabela:** horários de atualização sem um novo quadro programado, somados nas seis fases de cada cenário. Um intervalo vazio e um descarte por fila são acontecimentos diferentes.

| Cenário | v320 | Integração anterior | Nova integração |
|---|---:|---:|---:|
| 60/60 estável com antecipação | 0 | 0 | 0 |
| 60/60 com variação de chegada até 3 ms | 0 | 0 | 0 |
| 60/60 com antecipação e um callback omitido a cada 30 s | 120 | 120 | **0** |
| Host e tela a 59,94 com antecipação e a mesma omissão | 120 | 120 | **0** |
| Rajada adicional de 9 ms, com antecipação | 3 | 3 | 3 |

No cenário principal, as bases antigas já exibiam p50/p95/p99 de **16,667/16,667/16,667 ms**, mesmo com 20 vazios em cada série. O maior intervalo era **33,333 ms**, o 1% low era **56,817 fps** e a fila transbordou 103 vezes nas seis séries. Na integração, o máximo foi **16,667 ms**, o 1% low **60,000 fps** e houve zero transbordamentos e zero substituições no mesmo horário. O maior p99 entre as fases para a espera de quadro pronto até o horário escolhido caiu de **65,303 para 18,306 ms**. Essa espera é uma parte da latência. A apresentação física e a resposta do mouse incluem outras etapas.

No cenário de 45 ms, chegou a haver **66,667 ms** entre horários com imagens novas. Na divergência 60/59,94 houve **199 descartes por fila cheia** no conjunto das seis fases, embora cada horário tivesse um quadro para exibir. Um host a 60,000 produz aproximadamente 3,6 quadros excedentes por minuto sobre uma tela a 59,94. A fila absorve parte do excesso no início. Na Box, vale ler a frequência real das duas pontas antes de atribuir um descarte à WAN.

A matriz também verifica a folga hipotética entre a decisão e o alvo de tela situado um ciclo após o horário escolhido. No cenário principal, todas as decisões da integração caberiam em orçamentos constantes de 2 ms ou 8 ms de trabalho. Se cada quadro exigisse 20 ms desde a decisão, **18.896 decisões** da integração chegariam tarde para esse alvo ao longo das seis séries, contra **73** na base anterior que acumulava espera. Isso identifica uma condição importante do ensaio. O tempo da GPU, as margens reais e as decisões adaptativas do compositor precisam ser lidos na Box. Os CSVs guardam os dados por fase e por orçamento.

## 14. Codecs, tempo de decodificação e Vulkan na Mi Box

**25 de novembro de 2026. MiWire Box 0.3.0-box.2 (324)**, código local `6a43f5b56f9c`, núcleo `489254d3`. O mantenedor esclareceu que os 6–7 ms se referem ao valor da linha “Tempo médio de decodificação”. Esse é o maior valor de média que ele observou durante a sessão. ### Alterações verificáveis desde a v323

| Caminho | v323 | v324 |
|---|---|---|
| Entrega direta ao decoder, Vulkan e perfil MiBox | Ao entregar o quadro atual, a thread que recebia o vídeo tentava obter de imediato um buffer para o seguinte. Se faltasse buffer, repetia pedidos de até 10 ms. | Faz uma consulta com prazo zero para a reserva. Em caso de indisponibilidade, volta ao recebimento. O quadro seguinte ainda espera quando realmente precisa de um buffer. Um buffer disponível continua sendo reservado. Os outros perfis conservam sua política de reserva. |
| Falta prolongada de entrada ou recuperação solicitada pela saída | No caminho síncrono, um decoder que só retornasse “tente novamente” podia manter a thread dentro do laço e impedir que ela chegasse à recuperação ou à verificação de travamento. | A cada retorno, verifica a solicitação de recuperação. Sem progresso, a espera obrigatória chega ao tratamento de travamento após cerca de 5 s, desde que o driver devolva o controle. |
| Início do cronômetro | Gravava a marca do quadro após o retorno de `queueInputBuffer`. A média pode até subir sob as mesmas condições; comparar os números de v323 e v324 diretamente não isola ganho físico. |
| Leitura durante a stream | Média das amostras válidas das duas janelas de estatísticas mais recentes. | No painel detalhado com MediaCodec e Vulkan, exibe média, maior tempo individual e quantidade de amostras no mesmo intervalo. Sem amostras indica espera. Durações a partir de 1 s continuam fora da estatística do decoder. Usar também gaps de apresentação e eventos de recuperação para investigar travamentos. |

As mudanças de entrada valem para os três formatos quando passam pelo mesmo caminho MediaCodec. O término do cronômetro é a observação do buffer de saída pela thread do aplicativo. A chamada de liberação para a Surface, a aquisição da imagem, a sincronização do buffer com a GPU, a apresentação e o HDMI vêm depois no caminho Vulkan normal. Espera por CPU e pressão dos buffers podem afetar a medida. Ela não isola o tempo de execução em silício nem mede todo o atraso movimento–imagem. A nova linha usa duas janelas de aproximadamente um segundo, atualizadas quando chegam quadros.

**Reprodução da espera.** Com um quadro novo agendado para 16.667 µs e um buffer que fica livre em 7.000 µs, o receptor da lógica anterior retorna em 7.000 µs e o da nova em 0 µs de relógio simulado. O próximo quadro é entregue em 16.667 µs nos dois casos. Se o buffer só fica livre em 20.000 µs, ambos entregam o quadro seguinte em 20.000 µs. Isso comprova que a espera especulativa deixou de prender o receptor, sem demonstrar 7 ms de ganho físico no decoder. O teste de saída antecipada faz o codec simulado entregar o quadro dentro da chamada de submissão e verifica que os 6 ms simulados são contabilizados exatamente uma vez.

Na árvore de fontes desta edição, a política de espera está em `CodecInputPoller.java`. Em `app/src/main/java/com/limelight/binding/video/MediaCodecDecoderRenderer.java`, a linha 1843 registra a submissão e a 2086 monta as estatísticas detalhadas. Em `app/src/main/jni/vulkan/vulkan_renderer.cpp`, as linhas 1164 e 1189 adquirem a imagem e seu buffer, e a 2559 prepara a importação no Vulkan.

### Escolha de formato e pesquisas de implementação

- **HEVC 8-bit SDR, 1080p60 a 35 Mb/s** é a referência para esta Box e monitor. A T4 tem encode HEVC em hardware e a Xiaomi especifica HEVC Main 10 até 4K60 para reprodução. O fork já configura opções do Amlogic em etapas. Na primeira tentativa, em 1080p60, pede taxa de operação de 240 e prioridade 0. A API descreve a taxa como pedido de planejamento de recursos. Aceitar a configuração não comprova frequência efetiva ou efeito de cada chave do fabricante. O fork evita a chave genérica de baixa latência em `c2.amlogic`. Uma correção publicada pelo Moonlight V+ documenta uma falha de HEVC em certos Amlogic com Android 14: o decoder inicializava, o contador indicava 60 fps e a tela exibia muito menos. O sintoma relatado pelo mantenedor é diferente. Esta edição conserva o perfil de HEVC que ele já usou com sucesso. [Xiaomi](https://www.mi.com/uk/support/faq/details/KA-567165/) · [Android MediaFormat](https://developer.android.com/reference/android/media/MediaFormat#KEY_OPERATING_RATE) · [Correção e condições no V+](https://github.com/qiin2333/moonlight-vplus/pull/575)
- **H.264 High 8-bit** é o candidato para um A/B na v324. O fork procura o perfil High e usa um decoder AVC disponível como fallback. A Tesla T4 codifica H.264 e o aparelho anuncia H.264. Uma sessão real mostrará se, à mesma taxa, o componente AVC dá uma média ou um pico menor com definição aceitável. As capacidades Android informam formatos e desempenho declarado; só os timestamps medidos revelam a latência desta unidade. [Matriz da NVIDIA](https://developer.nvidia.com/video-encode-decode-support-matrix) · [Capacidades dos codecs Android](https://developer.android.com/media/optimize/performance/codec)
- **AV1** continua disponível para negociação com hosts adequados. A T4 tem um NVENC e a matriz marca AV1 encode como indisponível. O aplicativo Android não acrescenta esse bloco ao host. Para avaliar o decoder AV1 da unidade em streaming seria necessário um host com AV1 adequado a 1080p60, ou uma fonte AV1 controlada no aparelho para testar apenas o cliente. Forçar encode em CPU na Azure alteraria dois lados do comparativo. A distinção também vale para split-frame NVENC, que depende de mais de um motor. [NVIDIA](https://developer.nvidia.com/video-encode-decode-support-matrix) · [Guia de split-frame](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html)
- **Vulkan e captura.** O fork já passa uma Surface ao MediaCodec, obtém o AHardwareBuffer do AImageReader, respeita a cerca que protege a escrita do decoder e importa o buffer no Vulkan. Isso evita uma volta dos pixels decodificados à CPU no caminho normal. A leitura de buffer de entrada não é a mesma operação que capturar o desktop. DXGI Desktop Duplication entrega uma superfície no Windows do host. Implementar captura no host seria outro projeto e seu tempo ocorre antes da medição dos 6–7 ms. Outra opção seria Vulkan Video: além de uma fila de decodificação compatível, cada formato precisa de suas extensões, perfis e formatos de imagem aceitos pelo driver da Box. A presença de Vulkan gráfico não comprova essas capacidades. [Microsoft DXGI](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) · [Vulkan Video](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_video_decode_queue.html) · [AV1 em Vulkan](https://github.com/KhronosGroup/Vulkan-Docs/blob/main/proposals/VK_KHR_video_decode_av1.adoc)
- **Outros métodos.** O caminho Vulkan do fork usa saída síncrona; a opção de callback assíncrono é condicionada à ausência do renderizador Vulkan e do modo host-timed. O prazo de 50 ms do dequeue de saída é o máximo de espera quando não há saída. Um buffer pronto pode ser devolvido imediatamente. Reduzir esse prazo indiscriminadamente aumentaria as sondagens. Enviar fatias antes do quadro completo depende da capacidade `FEATURE_PartialFrame` e de entrega incremental coordenada com montagem, perdas e recuperação da rede. Testar primeiro se a unidade aceita fragmentos e se a saída chega mais cedo; suporte a enfileirar partes sozinho não comprova redução de latência. [Android MediaCodec](https://developer.android.com/reference/android/media/MediaCodec) · [Capacidade de entrada parcial](https://developer.android.com/reference/android/media/MediaCodecInfo.CodecCapabilities#FEATURE_PartialFrame) · [Baixa latência e dependência do driver](https://source.android.com/docs/core/media/low-latency-media)

### Ensaios sobre os formatos

As cinco configurações receberam a mesma sequência de 60 quadros em 1920×1080, a 60 fps, YUV 4:2:0. A codificação foi feita em software. A sequência dos timestamps de apresentação dos pacotes permite contar quantas imagens um consumidor ideal precisaria guardar apenas por causa da ordem. Com H.264 sem B-frames, HEVC sem B-frames e AV1 em tempo real sem lookahead, os três emitiram os 60 timestamps em ordem. Esse experimento isola perda no receptor mesmo sem um enlace externo. O MiWire já pede `2048 × (packetSize + 16)` bytes de fila. Para pacotes de 1.024 bytes o pedido é 2.129.920 bytes. O kernel pode limitar o valor efetivo. O experimento não justifica encolher a fila para baixar ping, nem extrapolar uma dessas capacidades para o Android. [Semântica de SO_RCVBUF no Linux](https://man7.org/linux/man-pages/man7/socket.7.html)

### Como encontrar o maior bitrate sustentável em cada ligação

1. Fixar o host/região, a cena com movimento, HEVC SDR 1080p60, perfil de pacing, codec e Vulkan. Verificar o novo rótulo da rede quando o próximo APK estiver disponível. A etapa de medição por ICMP já pode ser usada com a v324.
2. Medir dois minutos em repouso até o roteador e até a VM e repetir durante a stream. O pacote de provas contém `medir-rota.py` para uma Box já acessível por ADB, sem instalar aplicativo. Informar os dois IPv4 reais e o nome de um JSON novo. As sondagens ocorrem em paralelo, aproximadamente uma por segundo para cada destino. O arquivo guarda sequências, respostas ausentes e p50/p95/p99. A leitura dos tempos foi testada com entradas controladas. Quando ICMP é filtrado, usar o RTT ENet durante a sessão e marcar a medição ICMP como indisponível.
3. Começar em 35 Mb/s por 10 minutos em cada meio. Se estiver estável, comparar 50 e 65 Mb/s. Se houver perdas ou crescimento persistente no p95, voltar ao intervalo entre a última taxa estável e a primeira problemática e refinar em passos de 5 Mb/s. Se houver folga em 65, usar o mesmo procedimento acima. Registrar tráfego real, RTT, variação, quadros perdidos e gaps/60s. Alternar a ordem cabo/Wi-Fi na repetição para reduzir o efeito do horário.
4. Confirmar cada taxa escolhida em uma sessão de pelo menos 30 minutos no horário normal de jogo. Guardar a maior taxa que mantenha a definição desejada, o RTT sob carga próximo ao repouso e a cadência estável, com o total de perdas observado. Uma sessão com zero perdas é um resultado daquela sessão. Ainda faltam medições desta unidade para atribuir limites de Mb/s e ms a cada meio.

### O que o hardware permite concluir

O UHL-300 reúne três portas USB e uma interface Ethernet Gigabit integrada. A Box tem um único conector USB 2.0. No cabo, mouse, teclado, receptor do controle e Ethernet dividem a conexão com o aparelho. Em USB 2.0 High Speed o limite nominal é 480 Mb/s. A 35 Mb/s são 4,375 MB/s de vídeo, cerca de 7,3% desse limite bruto. A conta exclui os demais dados, FEC e protocolos. O valor de 1 Gb/s que pode aparecer no roteador é a negociação do segmento Ethernet. A taxa USB efetiva, o chipset, o intervalo do mouse e a alimentação da unidade ainda precisam ser observados. [Exbom e Infokit](https://www.youtube.com/watch?v=Uos-mOijub0) · [Xiaomi](https://www.mi.com/uk/support/faq/details/KA-567165/)

O USB-IF dá para o repetidor de um hub High Speed um limite de 36 tempos de bit mais 4 ns, aproximadamente 79 ns a 480 Mb/s por travessia. O caminho completo do mouse também inclui o intervalo de consulta do dispositivo, agendamento pelo host, possível tradução USB Full/Low Speed, Android, envio ao host, produção do quadro e apresentação. Um mouse que efetivamente reporte a 125 Hz dispõe de um intervalo de 8 ms, a 1.000 Hz de 1 ms. No monitor a 60 Hz cada atualização leva cerca de 16,67 ms. Essas são escalas temporais. Nenhuma mede o atraso desta unidade. No USB as transferências de interrupção têm agendamento periódico, enquanto as de volume usam capacidade disponível. A simples presença de Ethernet no mesmo hub não permite inferir um atraso constante no mouse. [USB-IF](https://compliance.usb.org/index.asp?UpdateFile=Electrical) · [Modelo USB do Linux](https://www.kernel.org/doc/html/latest/driver-api/usb/usb.html)
